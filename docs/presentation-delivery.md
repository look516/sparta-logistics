# 배송 배차 신뢰성 확보

## 문제 상황

> **에러 상황은 모두 다르다. 그런데 이걸 하나로 처리하는 게 맞을까?**

오후 8시, 예능 방송에 A 상품이 나왔다.  
저렴하고 유용해 보였던 A 상품에 주문이 폭주했고,  
스파르타 물류에는 순식간에 대량의 주문이 쏟아졌다.

주문이 몰리자 연쇄적으로 배송에도 트래픽이 폭등했다.  
이때 우리는 **단순한 과부하인지, 서비스가 실제로 터진 건지** 구분해야 했다.

---

## 케이스 1. 배차가 동시에 충돌하는 경우

갑작스러운 주문 폭주로 여러 요청이 동시에 같은 배송 담당자에게 배차를 시도한다.

- 이건 **일시적인 충돌**일 수 있다.
- 그렇다면 주문을 바로 취소하는 게 아니라, **잠깐 기다렸다가 재시도**해야 한다.
- 그런데 기존 구조에서는 배송 생성 실패 시 즉시 실패 이벤트를 발행했다.

**→ 다음과 같이 처리했다:**

1. `@Version` 낙관적 락으로 동시 배정 충돌 감지
2. `@Retry` 로 100ms backoff, 최대 3회 자동 재시도
3. 재시도 초과 시에도 **주문 취소 없이** 미배차 상태 유지
4. `PendingAssignmentScheduler` 가 5분마다 미배차 건을 탐색해 자동 재배차

---

## 에러 분류 & 적용 기술

| 상황 | 예외 | 처리 |
|------|------|------|
| 배차 동시 충돌 (과부하) | `OptimisticLockingException` | `@Version` + `@Retry` 3회 (100ms backoff) |
| Retry 초과 후에도 미배차 | — | `PendingAssignmentScheduler` 5분마다 자동 재시도 |
| 외부 서비스 일시 다운 | `FeignException` | Circuit Breaker fallback |
| 없는 리소스 조회 | `FeignException.NotFound` | 즉시 skip (`ignore-exceptions`) |
| Kafka 메시지 포맷 오류 | `JsonProcessingException` | offset commit, 재시도 안 함 |

---

## 결과

- 일시적 과부하 → **주문 취소 없이** Retry → 스케줄러 2단계 자동 복구
- 영구 실패 → 즉시 skip으로 무한 재시도 루프 제거
- 실제 서비스 장애 → Circuit Breaker가 감지 후 fallback 처리

---

## 개선 방향

`delivery.created` 이벤트 발행 실패 시 자동 복구 메커니즘 부재  
→ **Outbox 패턴** 도입으로 '저장 성공 = 발행 성공' 보장 필요
